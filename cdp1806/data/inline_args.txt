# CDP1806 inline call-argument overrides
#
# Some subroutines take their arguments inline, stored in the caller immediately after the
# four-byte SCAL instruction. The callee reads them through R3 (LDA R3 for a byte, RLXA Rn
# while X == 3 for a 16-bit word) and SRET R3 then returns past them.
#
# The analyzer normally works this out from the callee itself. Use this file for the cases it
# cannot: loops that move R3, return paths that disagree, calls into code that is not fully
# disassembled, or a subroutine whose arguments you know better than the walk does.
#
# Format:
#
#   <callee-address>  <argspec>     # trailing comment
#
#   <callee-address>  hexadecimal, with or without a leading 0x
#   <argspec>         comma-separated list, in the order the arguments appear:
#                       b  one byte
#                       w  one 16-bit big-endian word
#                       p  one 16-bit word treated as a pointer: it gets a reference for any
#                          mapped target, including uninitialized RAM, where a plain w only
#                          gets one when the target is in initialized memory
#                     or the word "none" for a subroutine that takes no inline arguments.
#
# Entries here take precedence over auto-detection. A file named in the analyzer's
# "Override file" option takes precedence over this one.
#
# A line
#
#   program <text>
#
# gates everything after it on the program's name containing <text>, case-insensitively.
# Addresses are only meaningful for the firmware they were read from, so image-specific
# entries must be gated this way; otherwise they would be applied to any CDP1806 program that
# happens to have a call at the same address. Use "program *" to open it up again.
#
# Example:
#
#   6e6b  p          # LoadStringForDisplay - 16-bit string descriptor
#   6fa5  b          # delay_base_ticks - one byte

# ---------------------------------------------------------------------------
# TAMAC-18 V2.8 (ROM/TAMAC-18 V2.8 9513.bin)
# ---------------------------------------------------------------------------

program TAMAC-18

# Reads one 16-bit pointer with SEX 3 / RLXA RE at 1abe-1ac0. Auto-detection declines while
# the walk cannot get through the call to 4048, whose own body is not fully disassembled;
# observed arguments are 1C7E, 1C91 and 1CA4, all of which point into RAM.
1abe  p

# 04f0: increments a saturating 16-bit counter at an inline pointer.
04f0  p

# 5000: digits_to_binary16 - the inline word is a digit COUNT, not an
# address, so b,b rather than w. Both sites pass a small number (3 at 5039,
# 4 at 52e9) which falls in ROM range, and 'w' references any target in
# initialized memory. Same reasoning as 290a below.
5000  b,b

# 5227: step_state_machine - a 2-byte pointer to a two-word descriptor
# {range table, state table}. SEX R3 / RLXA RE at 5227-5228.
5227  p

# 54b5: parse_digits_into - takes a 2-byte destination pointer, read by
# SEX R3 / RLXA R8 at 54b5. Without this the argument bytes disassemble as
# code; at 54ae they render as GLO R5 / LDN R1. The tell is the call at
# 549f: a four-byte SCAL whose next real instruction is the LBNZ at 54a5.
54b5  p

# 290a: memset, but DOWNWARD - its loop is STXD/DBNZ, so the pointer is the
# TOP of the region filled. Args are dest pointer, fill byte, count word.
#
# The count is written b,b rather than w on purpose. It is a NUMBER, and
# neither existing word kind keeps it free of references: 'p' references any
# mapped target, and 'w' references any target in INITIALIZED memory
# (InlineArgsAnalyzer.wantsReference returns `kind == POINTER ||
# block.isInitialized()`). Every count at the five call sites - 0028 at 2cb6,
# 0010 at 5389/57b7/586e, 00ff at 6e1c - lies in ROM, so 'w' would
# manufacture data references to those low addresses. BYTE never references,
# so b,b models the two halves and leaves the listing clean. Same dodge the
# 038d notes below use for a little-endian word.
290a  p,b,b,b

# 2ecd: binary_to_ascii_digits - takes its DIGIT WEIGHTS inline. SEX R3 at
# 2ecf, then SM against M(R3) and IRX once per digit, three times, so three
# bytes are consumed: 100, 10, 1. Auto-detection cannot see it because the
# bytes are never loaded as operands, only subtracted through X.
#
# Without this the weights disassemble as code, and at both call sites the
# result is plausible enough to mislead: 2ea8 and 2ec5 render as
# OUT 4 / LDN RA / LDN R1, inventing a PORT 4 WRITE inside the credit renderer,
# which does not touch any port.
#
# An earlier version of this comment went on to claim those were the only OUT 4
# sites in the image and that port 4 is unused. That was wrong - the search was
# never done. Instruction-aligned OUT 4 (0x64) occurs at 75ab and 75b5 in
# flush_output_latches, at 5530, and at 6df3/6df9 in the reset block's X==P
# region.
2ecd  b,b,b

# 5032: store_reader_decimal_to_page80 - converts the reader's three decimal
# digits at 8024..8026 and stores the result into a page-80 cell named by one
# inline byte (LDA R3 / PLO R8 at 5042, after PHI R8 = 0x80). Auto-detection
# declines because the byte is consumed through R8 rather than used as an
# operand. Without this the argument decodes as code and the listing loses the
# single most important write in the credit path: at 346d the 0x5C reads as
# STR R6 and at 34c9 the 0x5F as LDN R7, both plausible enough to pass
# unnoticed inside a reader-message handler.
5032  b

# 75c6: a stub - INC R3 / SEX R2 / SRET R3. It does nothing but SKIP one
# inline byte, so a call to it is disabled functionality whose argument still
# sits in the ROM. Auto-detection cannot infer this: the routine never loads
# the byte, it only steps over it.
75c6  b

# 36b0: packs the two card-data nibbles at 8024/8025 into one byte at the
# destination given as a 2-byte inline pointer. SEX R3 / RLXA R8 at 36b0-36b1
# is the canonical inline-arg read. Without this the argument bytes decode as
# instructions: at 33a1 they read as GLO R0 / IDL, and an IDL inside a card
# reader message handler would hang the dispatcher - which is the tell.
36b0  p

# 5e1b: a fault-log counter updater. The inline reads are scattered and
# conditional - LDA R3 at 5e20, 5e36, 5e41 and 5e55, plus bare INC R3 skips at
# 5e28 and 5e5a - but EVERY path consumes exactly three bytes, so one callee
# signature covers it. Without this the argument bytes disassemble as code: at
# 5c4f they read as DEC R7 / LDN R5 / OUT 1, inventing a port-1 access.
5e1b  b,b,b

# --- 038d: variadic, so its call sites are pinned individually -------------
#
# 038d reads a different number of inline bytes depending on D at entry:
#
#   D != 0  ->  LBZ at 038e not taken; LDXA/PLO RA then LDXA/PHI RA at 0391-0394
#               consume 2 bytes, low byte first (little-endian, so b,b not w).
#   D == 0  ->  branch to 0398; LDXA/PLO RA consumes 1 byte, then RLXA R7 consumes a
#               16-bit pointer which 039c dereferences. 3 bytes: b,p
#
# No single callee signature can describe that. Auto-detection declines: once the nested call
# at 03ee resolves it reports "return paths disagree", and before that it declines for want of
# that nested signature. Either way '@' pins a signature to one call site.
@0201  b,b        # 01fe: LDI 0x1
@0211  b,p        # 020e: LDI 0x0
@02c9  b,b        # 02c6: LDI 0x1
@02f6  b,b        # 02f3: LDI 0x1
@0880  b,b        # 087d: LDI 0x1
@0891  b,b        # 088e: LDI 0x1

# 046e: takes one 16-bit pointer, read by the canonical SEX R3 / RLXA R5 at
# 046e-046f, and then re-points X at R5 so nothing further comes from R3.
# Auto-detection handles this shape, so this entry is belt-and-braces - but the
# one call site is worth the note. Without a signature the argument at 05EC
# decodes as `LDN R4 / OUT 6`, inventing a UART write inside the DLC tick
# chain, which is the same failure mode the 2ecd comment above describes.
# The observed argument is 0466, which holds the word 8EEA.
046e  p

# 3aa8: play_toggle_pattern - one 16-bit pointer to a null-terminated list of
# half-cycle durations, read by SEX R3 / RLXA RC at 3aa8-3aa9.
#
# Added because its absence TRUNCATES CALLER FUNCTION BODIES. With no signature
# the analyzer cannot find the return point, so flow stops at the call: Ghidra
# had exit_call_connected as 6fb3-6fc5 and enter_call_connected as 6fff-700e,
# both ending at their SCAL 3aa8 (6fc2 and 700b) instead of at the SRET R3 that
# really ends them. The visible effect is worse than a short body - the name
# sits on a 16-byte prologue and the reader cannot tell that the state work,
# including the M(8032) = 0xAA billing gate at 703c, belongs to it.
#
# Observed arguments are 3a9e, 3aa0 and 3aa4, the three tone patterns (10ba).
3aa8  p

# 026a: CopyCodeTo9733AndJump. ONE inline byte - and the callee never reads it.
#
# 026A memcpys 0x3F bytes from 040D to 9733 and then LBR 9733, so the routine
# that consumes the argument is the RELOCATED COPY: 9733 opens LDA R3, and by
# then SRET has restored R3 to 026A's own caller's stream. Auto-detection cannot
# possibly see this - it inspects the callee's prologue, and 026A's prologue
# only reads the memcpy's three arguments.
#
# The byte is written straight to the F000 control latch at 9737-973B, so it
# selects the memory window the checksum is then computed through. All three
# live call sites pass 0x02: 92B8 (inside the relocated 1CB7 block), 4461 and
# 5C6D. 1E6F is the dead ROM image of 92B8.
#
# Without this entry the byte decodes as code at each site - at 4465 it reads as
# LDN R2, which is harmless-looking and shifts everything after it.
026a  b

# 746d: clear_block_range(lo, hi) - two 16-bit pointers. Present in
# tools/ram_map.py's PTR_ARGS but missing here, so tools/dis.py decoded the
# arguments as code: at 2F09 the bytes 88 65 88 B9 read as
# GLO R8 / OUT 5 / GLO R8 / PHI R9, inventing a port-5 write inside
# init_8865_block. They are the range 8865..88B9 that section 10bf describes.
746d  p,p
